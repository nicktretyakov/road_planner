# Route Planner Server — сервер планирования маршрутов доставки (Rust)

HTTP-сервер на **actix-web**, который строит маршруты доставки заказов по географическим
координатам: кластеризация по близости, маршруты с временными окнами (VRPTW), задача
коммивояжёра (TSP), поиск кратчайшего пути (Дейкстра), машинное обучение (онлайн-регрессия
времени в пути и UCB1-бандит выбора стратегии) и интеграция с готовым сервисом маршрутизации
OSRM с автоматическим фолбэком на Haversine + ML-прогноз.

Расстояния считаются **гаверсинусом из библиотеки [`geo`](https://crates.io/crates/geo)**
(`HaversineDistance` — большие круги на сфере, R=6371.0088 км).

## Быстрый старт

```bash
cargo run --release          # сервер на http://0.0.0.0:8080
# в другом терминале:
./scripts/demo.sh            # демо-сценарий с заказами Москвы
./scripts/smoke.sh 8099      # автотест всех эндпоинтов на отдельном порту
cargo test                   # 42 юнит-теста + 12 интеграционных
```

Переменные окружения:

| Переменная     | По умолчанию                          | Смысл |
|----------------|---------------------------------------|-------|
| `PORT`         | `8080`                                 | порт HTTP |
| `OSRM_URL`     | `https://router.project-osrm.org`      | базовый URL OSRM |
| `OSRM_ENABLED` | `1` (включён)                          | `0`/`false` — работать только на Haversine+ML |
| `RUST_LOG`     | `info`                                 | уровень логирования |

Хранение — **в памяти процесса** (по выбору пользователя): заказы, планы и ML-состояние живут
до остановки сервера.

## Архитектура

```
src/
├── main.rs               запуск actix-web (PORT, OSRM_URL, OSRM_ENABLED, RUST_LOG)
├── lib.rs                модули библиотеки (lib + bin, тесты интеграции переиспользуют lib)
├── api.rs                REST-хендлеры (см. справочник ниже)
├── planner.rs            оркестратор: K-means → матрицы → VRPTW-вставка → улучшение → ETA
├── storage.rs            состояние в памяти: заказы, планы, ML-движок, OSRM-клиент
├── models.rs             заказы/курьеры/планы/DTO, валидация координат
├── geo_core.rs           Haversine (crate geo), проекция в км, окна "ЧЧ:ММ-ЧЧ:ММ"
├── graph.rs              точки как вершины графа, рёбра — расстояния; Дейкстра на сетке дорог
├── algorithms/
│   ├── nearest.rs        жадный «ближайший сосед» от текущего местоположения
│   ├── kmeans.rs         K-means++ (детерминированный, по сиду)
│   ├── tsp.rs            TSP: NN + 2-opt + Or-opt + имитация отжига
│   └── vrptw.rs          маршруты с временными окнами: жадная вставка (Solomon) + симуляция
├── ml/
│   ├── sgd.rs            SGD-регрессия времени в пути (онлайн, L2, час-пик признак)
│   └── bandit.rs         UCB1-бандит: выбор стратегии улучшения маршрутов
└── osrm.rs               клиент OSRM /table (ureq, таймаут 4 с) + парсер матриц
```

## Как решается задача планирования (`POST /api/plan`)

1. **Кластеризация** — заказы проецируются в локальную плоскость (км) и разбиваются
   алгоритмом **K-means** (инициализация k-means++, Ллойд-итерации) на группы по числу
   курьеров (если не задан — эвристика ~6 заказов на курьера). Число кластеров = число
   маршрутов.
2. **Матрицы расстояний/времён** — для каждого кластера + склада:
   - если `use_osrm=true` и OSRM доступен — матрица `/table/v1/driving` (реальные дороги);
     поверх времён OSRM применяется ML-коэффициент дорожной загрузки (если есть история);
   - иначе — **фолбэк**: расстояния Haversine (crate geo), время = SGD-модель
     (базовая городская скорость ≈30 км/ч + «час пик»).
3. **Построение маршрута (VRPTW)** — жадная вставка в духе Solomon: кандидаты сортируются
   по срочности (кто раньше закрывает окно — тот первым), для каждого перебираются позиции
   вставки; стоимость = добавленное расстояние + взвешенное ожидание. Прибытие раньше
   открытия окна разрешено (курьер ждёт), опоздание — запрещено; неуложившиеся заказы
   возвращаются списком `unassigned` с причиной.
4. **Улучшение** — стратегию выбирает **UCB1-бандит** (по накопленным наградам): 2-opt,
   Or-opt (перенос отрезков 1–3), их комбинация или **имитация отжига** (метод, имитирующий
   природный процесс управляемого охлаждения: вероятностный приём ухудшающих шагов с
   остывающей температурой). Любое улучшение перепроверяет допустимость всех окон.
5. **Расписание** — на финальной последовательности считается ETA каждой доставки
   (часы «ЧЧ:ММ», ожидание окна, плечо в км/мин), замкнутые маршруты получают возврат на
   склад (постановка TSP — «посетить все точки один раз и вернуться в исходную»).
6. **Обучение** — награда бандита = процент сокращения маршрута относительно жадной вставки;
   план и след работы алгоритмов (`algorithm_trace`) возвращаются клиенту и сохраняются.

## Машинное обучение

| Компонент | Что делает | Где виден |
|-----------|------------|-----------|
| **K-means** | географическая кластеризация заказов | `algorithm_trace`, `last_clusters` в `/api/ml/stats` |
| **SGD-регрессия** | прогноз времени в пути `f(расстояние, час-пик)`; онлайн-дообучение на каждой фактической поездке; L2-регуляризация; скользящий MSE; физический пол (не быстрее 60 км/ч) | ETA в `/api/nearest`, времена в VRPTW, `traffic_factor` поверх OSRM |
| **UCB1-бандит** | выбор стратегии улучшения маршрута по награде (сокращение маршрута); сначала каждый рычаг по разу, затем argmax(μᵢ + c√(lnT/nᵢ)) | `strategy` в плане, `bandit` в `/api/ml/stats` |

Обратная связь: `POST /api/ml/feedback` — массив фактических плеч `{от, до, фактические
минуты, время выезда}`. Модель сразу дообучается — следующее планирование использует
обновлённые веса. Демо-набор может сгенерировать синтетическую историю поездок
(`{"with_feedback": true}`) — данные честно помечены как синтетика для демонстрации обучения.

## Справочник API

| Метод | Путь | Назначение |
|-------|------|------------|
| GET  | `/health` | состояние сервера (заказы, планы, OSRM) |
| POST | `/api/orders` | создать заказ/массив заказов (id назначается, если не передан) |
| GET  | `/api/orders` | список заказов |
| DELETE | `/api/orders/{id}` | удалить заказ (404, если нет) |
| DELETE | `/api/orders` | очистить все заказы |
| GET  | `/api/plans` | история планов |
| POST | `/api/plan` | план доставки: кластеризация + VRPTW + улучшение |
| POST | `/api/tsp` | TSP по точкам (первая — старт), закрытый/открытый тур |
| POST | `/api/nearest` | ближайшие заказы от текущего местоположения (жадный NN) |
| POST | `/api/dijkstra` | кратчайший путь по сетке дорог (Дейкстра) |
| POST | `/api/ml/feedback` | обучение SGD на фактических поездках |
| GET  | `/api/ml/stats` | веса SGD, статистика бандита, кластеры, статус OSRM |
| POST | `/api/demo/moscow` | загрузить 12 заказов по Москве (+опционально синтетический фидбек) |

### Формат заказа

```json
{
  "name": "Тверская, 7",
  "lat": 55.7615, "lon": 37.6094,
  "time_window": "09:00-11:00",
  "service_min": 8.0,
  "weight_kg": 2.0
}
```

### Примеры

```bash
# план на 3 курьеров от Красной площади с возвратом на склад
curl -sS -X POST localhost:8080/api/plan -H 'Content-Type: application/json' -d '{
  "couriers": 3,
  "start": {"lat": 55.7539, "lon": 37.6208},
  "start_clock": "09:00",
  "return_to_start": true,
  "use_osrm": true
}'

# замкнутый тур TSP (все точки один раз + возврат в старт)
curl -sS -X POST localhost:8080/api/tsp -H 'Content-Type: application/json' -d '{
  "points": [{"lat": 55.7539, "lon": 37.6208}, {"lat": 55.7615, "lon": 37.6094},
             {"lat": 55.7485, "lon": 37.5920}, {"lat": 55.7940, "lon": 37.5770}],
  "return_to_start": true,
  "method": "auto"
}'

# ближайший заказ для курьера в текущей позиции
curl -sS -X POST localhost:8080/api/nearest -H 'Content-Type: application/json' \
  -d '{"lat": 55.7539, "lon": 37.6208, "k": 3, "clock": "09:00"}'

# кратчайший путь (граф: узлы решётки ~1 км, рёбра = Haversine × 1.25)
curl -sS -X POST localhost:8080/api/dijkstra -H 'Content-Type: application/json' \
  -d '{"from": {"lat": 55.7539, "lon": 37.6208}, "to": {"lat": 55.8220, "lon": 37.6400}, "step_km": 1.0}'
```

Ответ `/api/plan` содержит: `strategy` (выбор бандита), `distance_source` (`osrm` или
`haversine+ml`), маршруты курьеров с ETA/ожиданием/окнами, `return_leg` (возврат на склад),
`unassigned` с причинами и `algorithm_trace` — пошаговый след работы алгоритмов на русском.

## Интеграция с внешними сервисами маршрутизации

- **OSRM** (по умолчанию) — открытый движок на данных OpenStreetMap: матрица времён и
  расстояний `/table/v1/driving`. Координаты передаются в формате `lon,lat` (см. `osrm.rs`).
- **GraphHopper / Google Maps Distance Matrix** — требуют другой протокол и/или ключ; точка
  интеграции одна: `OsrmClient::table` (возвращает минуты + километры). Подмена клиента
  на другой сервис не затрагивает алгоритмы.
- Сервис недоступен → автоматический фолбэк Haversine+ML, план всё равно строится
  (в `algorithm_trace` появится строка о фолбэке; статус OSRM виден в `/api/ml/stats`).

## Тесты

54 теста: юнит-тесты каждого алгоритма (известные расстояния Москва—СПб, сходимость SGD,
эксплуатация лучшего рычага UCB1, корректность окон VRPTW, улучшение 2-opt, Дейкстра на
рукотворном графе и сетке, парсер OSRM, сериализация окон) и интеграционные сценарии REST
(CRUD заказов, полный план с проверкой окон и замкнутости, TSP, nearest, Дейкстра, обучение
ML, накопление бандита между планами).

```bash
cargo test          # все тесты
./scripts/smoke.sh  # живой прогон сервера со всеми эндпоинтами
```

## Ограничения и развитие

- Хранение в памяти — при перезапуске данные исчезают (по требованию заказчика); для
  продакшена — слой `storage.rs` заменяется на PostgreSQL/Redis без изменения API.
- VRPTW без грузоподъёмности и многоштабных ограничений: вес заказов отображается
  (`load_kg`), но не проверяется. Следующий шаг — вместимость (CVRPTW) и несколько складов.
- Дейкстра считается по синтетической сетке (решётка с коэффициентом извилистости 1.25);
  с OSRM можно перейти на реальные графы (OSRM `/route` по парам точек).
- Бандит получает награду за план/TSP-вызов целиком; для тонкой настройки награду можно
  нормировать на время шага.
